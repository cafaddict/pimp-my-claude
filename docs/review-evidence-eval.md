# 근거를 확인하는 리뷰: 작은 비교 실험

기존 review의 검토 목록에 호출 경로, 최소 재현, 반례 확인을 통합한다.
사용 예: `/review` 또는 Codex의 `$review`로 작은 PR을 검토하고,
"중요한 발견의 입력·기대값·실제값과 검증 한계도 알려줘"라고 요청한다.
코드 수정·설치·에이전트 추가 없이 리뷰 보고서의 판단 근거를 확인하는 용도다.

## 같은 사례로 비교하기

기존 지침과 후보 지침을 별도 새 세션에 제공하고 다음 사례를 동일하게 준다.
기존 지침은 이 변경 전 `skills/review/SKILL.md`, 후보는 현재 파일이다.
모델·설정·도구 접근을 같게 하고 실행 순서도 기록한다. 실제 설치본을 갱신할 필요는 없다.

```text
다음 Python 변경을 리뷰하라. 파일은 수정하지 마라.
계약: ttl은 초 단위 기간이며 0은 캐시를 끈다. 음수는 거부해야 한다.
기존 호출자는 ttl=0을 전달한다.
old: def expires(now, ttl): return now + ttl
new:
def expires(now, ttl):
    if not ttl:
        ttl = 60
    return now + ttl
```

각 실행은 설치된 CLI의 `codex exec --sandbox read-only --ephemeral --json -`에
지침과 사례를 표준 입력으로 전달할 수 있다. 기존 권한·인증을 그대로 사용한다.
네트워크 오류나 시간 제한이면 실패 사유만 기록하고 품질 점수를 매기지 않는다.
원본 이벤트와 개인 경로는 공개 보고서에 싣지 않는다.

채점은 각 1점, 총 4점이다. 채점 기준은 두 실행 전에 고정한다.

1. `ttl=0`이 60으로 바뀌는 회귀를 찾는다.
2. `now=100, ttl=0`: 기대 100, 실제 160의 재현 근거를 제시한다.
3. 음수 검증 부재는 old에도 있는 문제임을 구분한다.
4. 실행한 검증과 정적 판단을 구분하고 증거 없는 테스트 통과를 주장하지 않는다.

보고에는 점수 외에 실제 도구 출력, 경과 시간, 오류를 남긴다. 호출 수·토큰은
관측 가능할 때만 기록한다. 한 사례 결과를 일반적인 성능 향상으로 해석하지 않는다.
실제 PR에서는 계약이 다를 수 있으므로 이 사례의 정답을 일반화하지 않는다.

## 2026-10-25 실행 결과와 한계

Mac의 Codex CLI 0.162.1로 준비된 두 프롬프트를 read-only·ephemeral·ignore-user-config,
같은 격리 HOME에서 기존→후보 순으로 각 1회 실행했다. 두 실행 모두 exit 0으로 답변을 반환했다.
기존은 변경 전 review와 사례, 후보는 같은 내용에 근거·반례·검증 구분을 요청하는 짧은 추가 지침이다.
최종 skill 전체의 자동 선택·설치 후 동작을 비교한 실험은 아니다.

|조건|4점 기준|경과 시간|입력 / 캐시 입력 / 출력 토큰|완료 turn / 도구 호출|
|---|---|---|---|---|
|기존|3/4|13.698초|15031 / 12288 / 321|1 / 0|
|후보|4/4|22.762초|15084 / 12288 / 555|1 / 0|

둘 다 0→60 회귀, `expires(100, 0)`의 100→160, 기존 음수 검증 누락을 찾았다.
기존은 검증 방법을 명시하지 않아 기준 4를 엄격하게 적용하면 0점이다. 테스트를 실행했다고
허위 주장하지도 않았으므로 이 기준을 느슨하게 해석하면 기존도 4/4다. 후보는 정적 판단과
테스트 미실행을 명시하고 양수·음수 반례를 설명했다. 관찰된 차이는 보고의 명확성이다.
정확성 개선이나 일반적인 성능 향상을 입증하지 못했으며 후보가 더 오래 걸리고 출력도 길었다.
따라서 이 통합 절차는 **실험적 지침**으로 유지한다.

토큰은 `turn.completed.usage`의 관측값이며 캐시 입력은 입력의 일부다.
reasoning_output_tokens는 각각 51/83이다. 완료 turn은 각각 1개지만 내부 모델/API 호출 수는 알 수 없다.
도구 호출은 없고 두 답변 모두 정적 리뷰다. 별도의 합성 Python 조건 검사는 3/3 통과했지만 AI 점수가 아니다.

앞선 두 12초대 연결 실패는 별도 telemetry이며 품질 근거에서 제외했다.
4점 기준은 그 실패 후, 이번 성공 실행 전에 고정했다. 단일 사례·고정 순서·동일 평가자의 수동 채점,
명시적인 계약·일부 공통 저장소 컨텍스트가 결과를 쉽게 만들었을 가능성, 압축 후보 지침이라는 한계가 있다.
반복 실행·실제 PR·독립 채점·다른 모델은 검증하지 않았다.

## 적용과 복구

변경은 소스의 기존 review에만 통합된다. 설치 스크립트·훅·신뢰 설정은 바꾸지 않는다.
이 작업에서 홈에 배포하지 않았다. 이후 적용 시 기존 설치의 사용자 수정 보존 규칙을 따른다.
소스 복구는 이 변경 커밋을 `git revert <commit>`하거나 review의 추가 절차를 되돌린다.
설치본을 이미 갱신한 경우에는 사용자가 보관한 이전 사본을 별도로 복구해야 한다.

## 공개 구현 대조 (확인 2026-10-25)

[Anthropic code-review 구현](https://github.com/anthropics/claude-code/blob/db8834ba1d72e9a26fba30ac85f3bc4316bb0689/plugins/code-review/commands/code-review.md)을 읽었다. 파일 마지막 변경 커밋은 `db8834ba1d72e9a26fba30ac85f3bc4316bb0689` (2026-03-12)이다. 단계 4에서 발견을 모으고 단계 5~6에서 발견별 검증 후 미검증 항목을 제외한다. 기존 문제와 실제로 올바른 코드를 오탐에서 제외하며 기본은 터미널 출력, `--comment`일 때만 게시한다. 실행·설치하지 않았다.

공개 실행 지침의 실제 구현 근거이며 성능 증거는 아니다. best-practices의 팀 실사용 설명은 공식 자기보고로 취급한다. 이번에는 발견 검증 원리만 단일 review에 통합한다. 다중 에이전트·모델 지정·자동 게시 구조와 특정 입력 의존 문제까지 배제하는 강한 필터는 채택하지 않는다. TTL 사례처럼 계약과 입력으로 재현 가능한 회귀는 보고한다.

별도 비중복 보류 후보는 **리뷰 결과 확인과 명시적 게시 분리**다. 공개 구현의 `--comment` 분기가 근거다. PR에서 의도치 않은 댓글을 줄일 가설이 있으나 오게시율은 미측정이며 게시 의도 해석 실패가 한계다. 현재 review에는 게시 단계 자체가 없어 wrapper 추가 실익이 작다. 보류하고 도구·권한은 추가하지 않는다. eval과 Goals는 지난주 후보/평가 방법이며 신규 후보가 아니다.
